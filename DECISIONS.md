# STEWARD — Technical Decisions (`DECISIONS.md`)

This document records the core architectural and engineering decisions made while building STEWARD, alongside the alternatives evaluated and rejected.

---

## ADR-001: Strict Separation Between AI Extraction and Payment Authority

- **Decision**: The AI model (`Qwen/Qwen3.6-35B-A3B-FP8` on NEAR AI Cloud) is invoked strictly as a stateless structured-output extractor (`tools: undefined`). It has zero access to signing keys, vendor registry mutation tools, policy configuration, or 1Click payment execution endpoints.
- **Alternatives Rejected**:
  - *Tool-calling agent with `execute_payment` tool*: Rejected because prompt injection embedded in untrusted invoice PDFs/text can coerce tool-calling LLMs into invoking payment tools with attacker-controlled parameters.
  - *LLM-as-a-Judge for fraud/policy decisions*: Rejected because probabilistic models can be socially engineered by pseudo-system instructions embedded inside invoice descriptions.
- **Rationale**: Enforces the core invariant: **AI extracts and explains. Code decides. Humans authorize exceptions.**

## ADR-002: Native Cryptographic Verification of Intel TDX v4 Quotes & NVIDIA GPU Evidence

- **Decision**: Implement a complete binary parser and cryptographic verifier in Node.js (`node:crypto`) for the `/v1/attestation/report` response from `https://cloud-api.near.ai/v1/attestation/report?nonce=<32-byte-hex>&model=<model>`.
- **What We Verify Cryptographically**:
  1. **Nonce Freshness & Format**: Generate a 32-byte (64 hex characters) CSPRNG nonce per analysis (we discovered during live testing that `cloud-api.near.ai` requires a 32-byte / 64-hex-char nonce and rejects 16-byte nonces).
  2. **Intel SGX/TDX X.509 PCK Certificate Chain**: Extract the 3 PEM certificates embedded in `intel_quote` (`Intel SGX PCK Certificate` → `Intel SGX PCK Platform CA` → `Intel SGX Root CA`), verify each signature up to the self-signed Intel Root CA (`SHA-256 fingerprint: 44:A0:19:6B:2B:99:F8:89:B8:E1:49:E9:5B:80:7A:35:0E:74:24:96:43:99:E8:85:A7:CB:B8:CC:FA:B6:74:D3`), and check validity timestamps.
  3. **Quoting Enclave (QE) Report Signature & Binding**: Verify the ECDSA-P256 signature over the 384-byte QE Report using the PCK leaf certificate's public key, and verify `QE_Report.REPORTDATA[0..32] == SHA256(AttestationPublicKey || AuthData)`.
  4. **TDX Quote v4 Header + TD Report Body Signature**: Verify the ECDSA-P256 signature over bytes `0..632` of `intel_quote` using the 64-byte `AttestationPublicKey`.
  5. **Hardware Measurements (`MRTD` & `RTMR0..3`)**: Extract `MRTD` (bytes `184..232`) and `RTMR0..3` (bytes `376..568`) directly from the cryptographically signed binary TD Quote Body and assert exact equality with `info.tcb_info`.
  6. **Signing Key & Nonce Binding in `REPORTDATA`**: Extract the 64-byte `REPORTDATA` field (bytes `568..632` of `intel_quote`) and verify that bytes `0..32` match the enclave's `signing_address` and bytes `32..64` match the exact 32-byte `nonce` generated by STEWARD.
  7. **NVIDIA Hopper GPU Attestation (`nvidia_payload`)**: Parse the GPU evidence list (`arch: "HOPPER"`), verify the embedded NVIDIA X.509 certificate chain and validity window, and verify `nvidia_payload.nonce === nonce`.
- **Alternatives Rejected**:
  - *Trusting HTTP 200 from `/v1/attestation/report` without binary verification*: Violates engineering rules and Track 03 requirements.
  - *Relying on external native C++ DCAP binaries*: Difficult to build portably across judge machines; Node's native `crypto.X509Certificate` and `crypto.verify('sha256', ..., { dsaEncoding: 'ieee-p1363' })` verify the exact ECDSA-P256 signatures in < 5ms with zero native dependencies.

## ADR-003: Built-in `node:sqlite` for Zero-Friction ACID Persistence

- **Decision**: Use Node.js's built-in `node:sqlite` (`DatabaseSync`) for storing the Vendor Registry, immutable Vendor Address History, Policy Configuration, Processed Invoice Decisions, Payment Quotes/Executions, and Audit Ledger.
- **Alternatives Rejected**:
  - *External PostgreSQL / Docker requirement*: Adds setup friction for automated hackathon screening (`Claude Code` / `Codex` evaluators) and human judges.
  - *`better-sqlite3` native C++ addon*: Requires `node-gyp` C++ compilation which frequently fails on newer Node versions (such as Node v26.7.0 present in this environment).
- **Rationale**: `node:sqlite` is built directly into Node.js, supports synchronous ACID transactions, requires zero external daemon setup, and enforces our privacy rule (only ledger metadata is stored; raw invoice files and text are never written to SQLite).

## ADR-004: NEAR Intents 1Click API Integration (`EXACT_OUTPUT` + Mainnet Reality)

- **Decision**: Integrate directly with `https://1click.chaindefuser.com/v0/tokens`, `POST /v0/quote`, `POST /v0/deposit/submit`, and `GET /v0/status`.
- **Key Findings from Live Investigation**:
  - The 1Click API operates on **mainnet** asset identifiers (e.g., `nep141:17208628f84f5d6ad33f0da3bbbeb27ffcb398eac501a31bd6ad2011e36133a1` for native NEAR USDC, `nep141:arb-0xaf88d065e77c8cc2239327c5edb3a432268e5831.omft.near` for Arbitrum USDC, `nep141:sol-5ce3bf3a31af18be40ba30f721101b4341690186.omft.near` for Solana USDC).
  - As confirmed by the official OutLayer documentation (`@outlayer/sdk`), NEAR Intents cross-chain swaps and gasless withdrawals operate on **mainnet only** (`swap` and `intentsWithdraw` do not exist on testnet).
  - However, `POST https://1click.chaindefuser.com/v0/quote` with `dry: true` works live without spending funds and returns real solver pricing, exact `amountIn` (including slippage buffer), `amountOut`, fees, ed25519 quote signature, and `correlationId`.
  - Setting `dry: false` locks a quote and returns a live single-use `depositAddress` for real settlement.
- **Design**:
  - In **Simulation Mode** (`STEWARD_MODE=simulation`), STEWARD fetches real live `EXACT_OUTPUT` quotes (`dry: true`) from `https://1click.chaindefuser.com/v0/quote` when online (with deterministic offline fallback if network is unreachable) and clearly marks the resulting payment lifecycle as `SIMULATED` without fabricating on-chain transaction hashes.
  - In **Live Mode** (`STEWARD_MODE=live`), STEWARD requests a live locked quote (`dry: false`) with a single-use `depositAddress` and polls `GET /v0/status?depositAddress=...`, gated behind `ALLOW_MAINNET_EXECUTION=true` so real funds are never spent without explicit product-owner authorization.

## ADR-005: Treasury Custody Architecture (OutLayer TEE Custody + Scoped Signer Fallback)

- **Decision**: Support OutLayer Agent Custody (`https://api.outlayer.ai`) as the primary TEE-backed custody provider, alongside a Policy-Gated Scoped Signer architecture.
- **Key Findings from Live Investigation**:
  - `@outlayer/sdk@0.1.0-alpha.4` defaults to `https://api.outlayer.fastnear.com`, which now returns `{"error":"api_moved","new_base_url":"https://api.outlayer.ai"}`.
  - `https://api.outlayer.ai/health` is live (`{"status":"ok","version":"0.1.0","git_sha":"451b270a070f"}`).
  - Therefore, our OutLayer custody adapter explicitly configures `baseUrl: process.env.OUTLAYER_API_BASE_URL || 'https://api.outlayer.ai'`.
  - We also document the exact security properties and limitations of OutLayer TEE custody vs. NEAR Function-Call Access Keys (which cannot natively attach arbitrary `1 yoctoNEAR` deposits required by NEP-141 `ft_transfer` unless calling through a dedicated treasury proxy contract) vs. a server-side policy-gated signer.
